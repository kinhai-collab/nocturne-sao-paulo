One-time organizer setup

A Google account.
A place at the table.

Diners choose up to five restaurants and sign in with Google. You see who voted and their selections in a private Sheet. The public page shows only aggregate totals.

What is ready?

Nocturne is the homepage. The hero rotates through eight attributed photos from Evvai and Tuju, every 10 seconds with a 1.5-second crossfade. The five-choice interface and Google-account verification backend are prepared. Google sign-in and shared storage are not active until the two configuration values below are supplied and tested.

1 / Publish the website

  1. Upload the contents of the supplied dist folder to your GitHub repository root.
  2. Settings → Pages → Deploy from a branch → main / root. Save and wait for a successful deployment.
  3. Copy the public URL GitHub provides. For Google configuration you need only the origin, for example https://kinhai-collab.github.io, without the repository path or trailing slash.

This website is published on GitHub Pages, independently of ChatGPT. No ChatGPT account is required. Workplace network rules may still block GitHub Pages or Google sign-in.

2 / Create a Google sign-in client

  1. In Google Cloud Console, create or select a project. Open Google Auth Platform and configure Branding and Audience for your dining poll. Use External if diners include personal Google accounts. Supply the contact, homepage and privacy details Google asks for.
  2. Create an OAuth client with application type Web application.
  3. Add your exact public website origin under Authorized JavaScript origins. You may also add http://localhost:8765 for local testing, and the Sites preview origin if testing there. Do not include a repository path.
  4. Copy the public client ID ending in .apps.googleusercontent.com. You do not need to put a client secret in the website.
  5. While Google’s app is in Testing, add your intended test accounts if required. Complete the Audience/publishing configuration Google requires before inviting general diners.

This uses Google’s official sign-in button and basic identity claims only. Diners do not grant access to their Gmail or Google Sheets.

3 / Connect the private Sheet

  1. Create a private Google Sheet. Open Extensions → Apps Script.
  2. Replace the editor's Code.gs with the supplied Code.gs. Add a second Script file named Forge and paste Forge.gs. Keep both files in the same Apps Script project. Library license.
  3. Run setup() once and authorize the organizer's script access. It creates a new tab named VotesGoogleV2; an existing anonymous Votes tab is preserved.
  4. Project Settings → Script Properties: add GOOGLE_CLIENT_ID with the public client ID, and ALLOWED_ORIGINS with the exact site origin. Multiple origins can be comma-separated. SHEET_ID was set by setup().
  5. Deploy → New deployment → Web app. Execute as yourself; access for Anyone. Keep the Sheet private. Copy the URL ending in /exec. Organization policies can restrict this deployment option.
  6. Edit the site's config.js: set endpoint to the /exec URL and googleClientId to the same public client ID. Keep pollId as sao-paulo-2026. Publish the updated files.

4 / Confirm sign-in and tracking

  1. Use HTTPS, sign in with a test Google account and select up to five restaurants. Submit. The page should explicitly say Google Sheets confirmed the ballot.
  2. In your private VotesGoogleV2 tab, confirm the row contains Timestamp, Poll ID, Google account ID, Name, Email, Choices JSON and readable Restaurant names.
  3. Sign in from another device with the same account. Retrying the same ballot must not create another row; a different ballot should be rejected.
  4. Use a second Google account to submit a different ballot. Verify that it appears as a separate voter.
  5. Check public results: only counts should appear. Do not publish the Sheet or share its edit link with diners.

End-to-end Google login, iframe acknowledgement and actual Sheet writes are unverified until these organizer settings are deployed. Local checks cover cryptographic signatures, token claims, identity storage, five-choice validation and duplicate rejection.

How it tracks people

The Google account's stable ID is the duplicate-vote key. Name and email are stored for your convenience. The backend checks the token’s Google signature, client ID, issuer, expiry, verified-email flag and short-lived sign-in challenge before saving anything. It uses Google's rotating public certificates and the bundled Forge RSA verifier. Tokens stay in page memory and are not saved to browser storage or the Sheet.

Each Google account receives one immutable ballot. This prevents the same account from voting again from another device; someone with multiple Google accounts can still submit more than once. Public results expose totals only. The private Sheet is the organizer's view of who selected what. Decide a retention period and include your contact information in the privacy notice before launch.
