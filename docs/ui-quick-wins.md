# Dinner planner quick wins — batch 1

Front-end changes only. No backend schema, API, reservation values, or permissions changed.

1. Active dinner details have one primary next step. When a guest response form is rendered, the top section is a short Your turn prompt (using the host name for RSVP when available), and the sticky form submit is the primary. Receipts instead have one primary Change my response action, without another edit button in the receipt. Organizer availability is secondary and not sticky; Save plan is also secondary so expanding the controls does not add another primary. A post-render guard keeps only the next-step owner primary. When the top step is Share invitation, the share card keeps Copy invitation and WhatsApp without repeating Share invitation. Home cards use the derived action label.
2. `EnkaiDinnerState.derive()` supplies the single dinner status line and action labels. Reservation labels are Not reserved yet / Reserved / Reservation reconfirmed / Walk-in only; stored values remain unchanged. Search distinguishes Choose this restaurant from Add to shortlist. Group discovery says Ask the group.
3. Organizers see option rows with counts, proportional bars, voter names, a unique leading option, and none counts without opening a select. Tied leaders are named in the next-step hint with their shared count; neither date nor restaurant is preselected on a tie. Finalize selects remain available.
4. Calendar connection status and its optional Connect calendar button appear once. Option notes show actual conflicts or checked clear results only. Each open poll dimension requires a real choice or an explicit, mutually exclusive None of these work; untouched forms show an inline error. None is submitted as the existing empty array, without a new backend flag.
5. Create, availability, RSVP, plan, cancellation, and refresh requests show a visible busy label and `aria-busy`, disable the relevant controls, and restore them after success or failure. Dinner saves receive the triggering submitter or clicked cancel/group-pick/group-vote button explicitly. Only that button gets the saving label and `aria-busy`; other save buttons keep their labels while disabled. Prior disabled/busy state is restored.
6. Cancelled details show a banner and Copy cancellation message, including known date and place. They have no invitation share card, response form, next action, or calendar connection prompt. Home uses View.
7. New plans start with the device time zone when no city is entered. Recognized cities fill the destination zone and collapse its details; unknown cities open the editable zone choice. A manual time zone survives city edits, restaurant-city selection, and draft restoration until the host clears the select. Named progress preserves the original structure: restaurant flow Where (destination + restaurant) → When → Who → Review; date flow Where & when (destination + times) → Place → Who → Review; undecided flow Where & when → Who → Review. The current progress label has `aria-current="step"`.
8. Organizer sharing fallback counts other people's responses, so saving only the host's availability still offers Share invitation. Guest final plans needing an RSVP or reconfirmation use the rsvp-needed stage even when Unbooked; the status label still describes the reservation.

Permitted HTML entry points, invitation pages, and the invitation preview generator use `v=20261127`. Protected generated/native directories were left untouched.

## Group/agent compatibility notes

- `dinner-state.js` is a pure UMD module usable in browsers or Node. `derive(meal, {now, role})` returns the stage, display status, stable next-action ID, tallies, unique leaders, and none counts. It also exposes `otherResponseCount` (subtracting the organizer's own vote for organizers) and `tiedTimes` / `tiedRestaurants` arrays of structured option values. Tallies and hints include every response without special host weighting. Tied and zero-vote options produce no leader; tie arrays contain only shared positive leaders and preserve option order. The UI dispatches `nextAction.id` to existing actions. Response-form prompts and primary-button ownership are presentation choices; dinner stage and next-action logic remain centralized in `derive()`.
- Availability stays in arrays of ISO instants and restaurant names. None controls use separate form-only fields; payload vote arrays contain only existing structured values. Drafts preserve explicit none choices. Server empty arrays are not automatically selected as None, since old records may predate a newly opened poll dimension. Tallies report existing empty arrays as none counts; legacy empties cannot reliably distinguish intentional none from a dimension that was not open when a guest responded.
- Current agent blockers remain: plan finalization and restaurant discovery are organizer-gated; `selectedTime` and `restaurant` allow one final choice each; roles and attendance include legacy organizer-specific behavior. There is no shared negotiation state, proposal history, per-dimension response version, or agent authorization model. A backend change would be required to distinguish legacy none responses and stale responses to new options.
- Planning drafts and manual busy blocks are client-only. Saved guests and restaurant wish lists are per-device names, not account identities, group membership, delivery records, or shared availability. Connected-calendar conflicts are private to the current user, not a group scheduling dataset.
- Group discovery currently takes the organizer's agreed date, searches up to three recommendations, and cannot verify group seating or booking availability. Existing invitation previews expose limited dinner fields and photo results and are not a complete negotiation read model. Reservation recording remains manual; no agent booking or background coordination was added.
